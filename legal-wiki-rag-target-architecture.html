The Structured Wiki

Target architecture for a legal RAG system meant to serve any lawyer, in any organization, asking any kind of question — not just commercial-contract review. Every step from ingestion to query response.

§ 00

Scope

Nothing below replaces the retrieval and grounding pipeline already in production — hybrid RRF fusion, the independent grounding check, deterministic citation verification. Every addition either sits in front of it as a shortcut, or feeds it richer material at ingest time. Any question the new structured layer doesn't cover falls straight through to the exact pipeline running today.

Locked in — seven features

  • Playbooks
  • Precedent layer
  • Review Table, upgraded
  • Obligation & Deadline tracker
  • Contract Register
  • Risk / Deviation dashboard
  • Collections (shared plumbing under Playbooks & the dashboard)

All seven stay locked — but are now built family-aware off a schema registry, not shaped around commercial contracts by default. See Document Families.

§ 00.1 new

Document Families & Schema Registry

The current target schema — clauses[] / obligations[] / entities[] / relationships[] — is a contract schema wearing a general-purpose name. Serving "any lawyer, any question" means the extraction schema is looked up per document type, not hardcoded. The 24 folders in the working taxonomy cluster into five families.

Family 1

Bilateral commercial contracts

Consulting · DPA · Employment · Escrow · IP Assignment · Joint Venture · Lease · License · Loan · NDA · Service · SLA · SPA · Shareholder · Subscription · Supply — 16 of 24 folders

Parties, clauses, obligations, dates, termination/renewal. Already well served by the existing clauses/obligations schema — minimal change needed.

Family 2

Deal-stage / pre-binding

Term Sheet

Proposed terms, not obligations. Carries a binding_status flag, exclusivity window, conditions precedent — otherwise forcing it through the obligation schema risks misrepresenting indicative terms as enforceable.

Family 3

Litigation / dispute

Court Judgment · Pleading · Brand Judgements

Case citations, procedural posture, holding, relief granted, parties as plaintiff/defendant. Needs paragraph-level structural anchoring and citation extraction — nothing to do with clause/obligation.

Family 4

Corporate / authorization instruments

Board Resolution · Power of Attorney

Grants of authority, not agreements. Schema: grantor, grantee, scope of authority, effective/expiry, limitations, resolving body.

Family 5

Advisory

Legal Opinion

Addressee, matters opined on, assumptions/qualifications, conclusion, scope-of-reliance limitation. An opinion advises — it doesn't obligate anyone.

Residual

Ungrouped / generic fallback

Whatever doesn't match Families 1–5

Today's "Ungrouped" folder is a live signal, not just a bucket — the generic fallback schema matters more the moment this system serves a second organization with a different document mix.

Classification mechanism — revised: content-primary, folder-assisted

Doc-type classification runs on every document regardless of whether a folder is present — one mechanism, not two separate code paths for "filed" vs. "ad-hoc upload." A bulk/library upload with folder placement gets a confidence boost when content classification agrees with the folder — resolves fast, low Review Queue hit-rate. An ad-hoc single-file upload (chat, Review/Compare/Draft — no folder context exists there by definition) runs on content alone, same threshold, no boost available.

Folder raises confidence when it agrees, never lowers scrutiny when it might disagree. A document sitting in the wrong folder (mis-filed, legacy structure, human error) still routes to the Review Queue as a mismatch — folder is never trusted as ground truth over what the content actually says. No taxonomy is required from the user to make this work; the 5 families are the system's internal schema, not a filing structure lawyers need to learn.

Open item — family set is a first cut

The 5 families were derived from this org's own 24-folder list. Whether they hold up against a genuinely different organization's document mix (a trust deed, a regulatory consent order — anything outside this seed list) is untested. Watch what actually lands in the generic fallback once uploads from outside this list start arriving — that's the real signal for whether a 6th family is needed, not something to decide blind now.

Per-family metadata extraction

The existing page_metadata cache — what Review Table reads first, before falling to LLM extraction — is fixed to 12 hardcoded, contract-shaped fields (governing law, dates, caps, etc.). Same problem clauses/obligations had before the schema registry: a litigation doc doesn't have a liability cap, it has a case number, court, and disposition. Fix is the same mechanism applied here — the standard-field list becomes per-family, pulled from the schema registry rather than one fixed list for every document.

Low-confidence metadata values feed the same Review Queue, same stakes-tier split already built for clauses — not a separate mechanism. A low-stakes field (e.g. a contract's stated address) is bulk-accept eligible; a high-stakes one (governing law, liability cap) requires individual sign-off, same reasoning as lifecycle status. And because doc-type classification confidence gates which family's metadata schema even gets applied, a low-confidence doc-type call is arguably the higher-stakes flag of the two — it risks extracting the wrong set of fields entirely, not just one wrong value within the right set.

Open simplification — not urgent

Once family-specific typed tables (documents, contracts, litigation_facts, authorizations, opinions) hold typed values populated at ingest, page_metadata may be a redundant middle layer rather than a needed one. Worth deciding later: keep it as a denormalized fast-read cache, or drop it and read the family tables directly.

Clause sub-attributes new

A clause today is typed at the row level — clause_type, verbatim text, one typed value. For the clause types Playbooks/Review/Compare/Risk care about most, that single typed value flattens what's actually a small structured object. A limitation-of-liability clause isn't just "text + one number" — it's cap_present, cap_type (fees-paid / fixed-amount / multiple), cap_period, and an uncapped_exceptions[] list (fraud, confidentiality breaches, etc. are commonly carved out). Extracting that shape once, at ingest, means Playbooks/Review/Compare/Risk all read the same structured object instead of each re-interpreting the same clause text independently — the same "extract once, reuse everywhere" discipline already applied to clauses generally, one level more granular for the highest-value clause types. Scoped as an addition to specific clause types in the schema registry (starting with liability cap, termination, indemnity), not a rewrite of clause extraction generally.

Fig. 1 — Still seven stages, same shape as the original doc. Stage 02 now carries doc-type + jurisdiction alongside role/lifecycle; every extended stage grew a step, none were replaced.

01

File read + OCR

extended

pypdf first, OCR fallback under 50 chars/page — unchanged. A confidence classifier still decides whether Tesseract's output is good enough before ever calling Azure Vision, so the expensive vision model only sees genuinely difficult pages.

New in this revision: the page classifier gains two more classes beyond text / scanned — table-bearing and image/chart-bearing. Today, a table that extracts "successfully" by char-count still has its row/column structure silently flattened, and a chart on a page with >50 surrounding characters never triggers OCR at all — zero extraction of the visual content. Azure Vision also gains a second prompt mode: description, not just transcription, for chart/diagram pages — the existing strict-transcription prompt stays for scanned text.

Also new (planned, not present — the only per-page quality signal in the schema today is pages.char_count): each page persists its own quality provenance — OCR engine used, OCR confidence, character count, rotation/skew flag, detected language, table-detected flag — alongside the extracted text, not just a pass/fail signal. This is what makes a Document QA warning possible: a document with one or more pages below the confidence floor surfaces a plain-language flag to the lawyer at read time — "page 27 could not be reliably interpreted; analysis on this document may be incomplete" — rather than the gap staying invisible inside an internal confidence score nobody outside ingestion ever sees. Same non-blocking posture as everything else in Review Queue — a warning, not a block.

02

Role + lifecycle + doc-type + jurisdiction tagging

extended

Role (precedent / active-matter / both) and lifecycle (current / superseded) tagging as before — role still set by upload location, never by the AI reading it. Lifecycle status still always requires individual Review Queue sign-off, never bulk-accepted.

New in this revision: a document-type classification pass runs here too, upstream of the length fork — deciding which of the five schema families (or the generic fallback) applies before the synthesis call in stage 03 is even made. Runs content-first on every document, whether or not a folder path exists: folder placement, when present, is a confidence boost on agreement, never a substitute for running this pass, and never a reason to lower scrutiny when it disagrees with what the content shows (full mechanism in Document Families). A jurisdiction tag is added alongside it: a "notice period" or "reasonable time" standard means different things under different governing law, so jurisdiction can't stay implicit inside a contracts.governing_law field once the system spans multiple organizations. Low-confidence doc-type classification routes to the Review Queue — arguably higher stakes than a single misclassified field, since it determines what gets extracted from the whole document.

03

Adaptive synthesis call

extended

Same single-call-or-segments structure as today. Structured-output schema still grows alongside the wiki prose: clauses[], obligations[], entities[], relationships[] — every field still typed (date / currency / number / boolean / enum / text), still one extended call, not several new ones.

New in this revision:

  • Schema is no longer fixed — it's pulled from the schema registry by family (§ Document Families), with org-level overrides merged in before the call.
  • Page-count target and extraction emphasis become a per-family parameter, not the fixed "extract 10–30 pages, cover thoroughly" instruction — a citation-dense litigation doc needs finer granularity; a short opinion doesn't need padding to reach 10 pages.
  • New output fields, folded into the same call: citations[] (statute/case references, normalized), structural_anchors[] (section/¶ numbering), hypothetical_questions[] (see Retrieval Enhancements), tables[] and figures[] routed to their own structured stores rather than prose, and binding_status for Family 2 (term sheets).
  • relationships[] gains a doc-reference resolution sub-step — an in-text mention like "as defined in the Master Service Agreement dated..." gets fuzzy-matched against the documents registry (same mechanism class as entity canonicalization) and written as a resolved edge, or an explicit references-unresolved edge if no match is found — never silently dropped.
04

Merge + provenance

extended

Contradiction detection and source-attribution labeling continue for wiki pages as today. Every extracted clause, obligation, and entity still written with a confidence score and a pointer back to its exact evidence span.

New in this revision: a reconciliation/dedup step for structured rows (clauses, obligations, citations) that straddle a segment boundary — today's merge logic only dedupes wiki pages, not structured fields, and that gap now matters because structured extraction, not just prose, is happening per segment. Contradiction detection is also re-sequenced to run after amendment-chain edges (§ Cross-Document Relations) are written, so a superseded clause and its amendment aren't flagged as a contradiction instead of a resolved version chain.

05

Compaction

unchanged

Pages over 5 appends or 8,000 chars still get re-synthesized. Structured rows don't accumulate the same way prose does, so they don't need it.

06

Embeddings

extended

Page-level embeddings unchanged. Clause-level embeddings for the subset used in precedent matching, unchanged.

New in this revision: a third embedding type — hypothetical-question embeddings — generated per page/clause during the same synthesis call in stage 03, embedded alongside page content. Full rationale in Retrieval Enhancements.

07

Evaluation gate

new

Every extracted clause, obligation, and entity carries the confidence score it was born with. Below threshold, it lands in the Review Queue instead of entering the index silently.

New in this revision: the same threshold logic now also covers doc-type misclassification confidence and table/figure extraction confidence — not just clause/obligation fields.

Segmentation — mechanism change, not just schema growth

Today's segmentation is a blind 40,000-char cut with 500-char overlap — arithmetic, no respect for document structure. That was tolerable when only prose pages were being merged; it isn't once structured rows (clauses, citations) are being persisted, since a blind cut can split a clause or sever a citation string mid-way, producing duplicate or garbled DB rows. Fix: run the structural-anchor parse (cheap regex pass) before the segmentation decision, and segment along section/¶ boundaries — packing sections up to the ~40k budget instead of cutting blind. This removes the split risk at the source rather than papering over it with overlap.

§ 01.1 new

Tables, Charts & Images

Confirmed absent from both the current system and the original Part 2 target — not a mechanism to upgrade, genuinely new scope. Today, a table-bearing page either extracts successfully with its row/column structure silently destroyed, or — if scanned — gets transcribed as loose text at best. A chart or diagram on a page with >50 surrounding characters never triggers OCR at all: zero extraction of the visual content, silently.

Tables — own path, not squashed into wiki prose

Table pages route to structured extraction (vision-LLM with a table-output prompt, or a dedicated table-parse step). Output is rows/columns as typed data, not a prose sentence, stored in a new tables table with the same evidence-pointer and confidence discipline as everything else. The wiki page can reference that a table exists and summarize it, but the exact values live in the structured store — queryable, citation-checkable. Prose-only storage makes exact numbers unrecoverable and unverifiable, which is the worst possible spot for hallucination given a wrong payment figure carries real consequence. A markdown-serialized fallback representation of the table is also worth keeping alongside the structured rows, so the wiki-prose layer can still reference table shape even without hitting the structured store directly.

Calculations — split into two separate targets

A rule/formula ("cap = 2× fees, prior 12 months") is a clause — prose + typed value, existing path. A computed value (the actual numbers in a payment schedule) is a table. These answer two different lawyer questions — "how is the cap calculated" versus "what is the cap today" — and conflating them into one page loses one or the other.

Charts, diagrams & images shipped

Routed to the vision-LLM under the new description prompt mode (not the transcription-only mode used for scanned text). Output is a synthesized wiki page tagged as image-derived, plus a pointer to the source image, stored in a new figures table alongside a generated description and confidence score.

Shipped, with one correction the design did not anticipate: the description prompt mode was reached only through the page classifier's structural pass, so in practice every figure row on the live corpus was written by the ordinary synthesis call instead — extraction_method='synthesis', describing the figure from the page's text. See § 01.3 for what that produced and how it was corrected.

Cost — genuinely new, not folded-in

Unlike citations, jurisdiction, or entity canonicalization — all of which ride free inside the existing synthesis call — table and image extraction require real new vision-model calls. This is a new cost category, scaling with how table/image-dense the actual corpus is, which is currently unmeasured.

§ 01.2 new

Cross-Document Relations

The original relations table already extends to party↔clause, clause↔clause, and document↔document (precedent lineage) edges, and shared-concept pages already merge across documents implicitly. What the brainstorm surfaced is everything that's not covered by those three edge types.

amends /
superseded-by
Amendment chains — not the same as precedent lineage. Precedent lineage means "we've used this clause language before, in a different deal." This means "this is the same deal, version 2." The lifecycle column (current/superseded) must derive from this edge, not be set independently, or the flag and the graph drift apart.
ancillary-to
Transaction clusters — genuinely new, nothing covers this today. Real deals ship as a bundle (SPA + Shareholder Agreement + Escrow Agreement) that cross-reference each other. A lawyer asking about the SPA's indemnity terms probably also needs the Escrow Agreement's release conditions.
litigation-
disputes
Links a litigation_facts row to the specific clauses row it's litigating — only possible now that litigation is its own schema family with its own structural anchors.
references-
unresolved
An in-text document reference that couldn't be fuzzy-matched to anything in the documents registry — written explicitly rather than silently dropped, since "the referenced document isn't even in our system" is itself useful for a lawyer to know.
defines /
references-term new
Defined-term cross-reference — genuinely absent today. A clause defining "Affiliate" in §1.2 and every clause that later relies on that term (§4.3, §8.2, §12.1) are structurally unlinked right now; the term is just prose. Written at the same synthesis call as other relations: the definition clause gets a defines edge to the term, and each subsequent clause using a capitalized defined term gets a references-term edge back to its definition. Answers "where else does this contract rely on how we defined X" and "is this term actually defined anywhere in this document" — the second one currently answerable only by an LLM re-reading the whole document.

Entity-based aggregation ("every contract with Acme Corp") is already handled by entities/entity_aliases canonicalization — no new relation type needed there, just reaffirming it as the answer to that shape of question.

Retrieval-side consequence

Structured cross-doc questions ("show me every amendment to this MSA," "what else is part of this transaction") resolve via a SQL join over relations/entities — same fast-path tier as a clause lookup, not the broad-retrieval fallback (80 candidates, per-doc cap 4). Broad retrieval stays the fallback only for cross-doc questions the relation graph doesn't structurally cover.

Named, bounded-hop functions new

The relation fast path should be a set of typed, named operations — find_agreements_by_party(), find_change_of_control_terms(), find_expiring_contracts() — rather than open-ended joins assembled per question. Each caps its own traversal depth: 0 hops for a direct lookup, 1 for a basic relationship, 2 for the common multi-hop cases (amendment chain, transaction cluster), 3 as a hard ceiling for rare compound cases. Cheap governance on something already built — bounds worst-case query cost and keeps every relation query auditable as one of a known, finite set rather than an arbitrary graph traversal.

Cost: no new category — rides inside the existing relationships[] extraction, same call, wider edge-type vocabulary. Doc-reference fuzzy-match is the same cheap class as entity canonicalization. Defined-term edges are the same pattern again — one more edge type in the same call, not a new extraction pass.

§ 01.3 new

Retrieval Enhancements

Hypothetical-question embeddings

At ingest, alongside normal page synthesis, the LLM generates 3–5 questions a page/clause plausibly answers — phrased how a user would ask, not how the document reads. Those get embedded too, pointing back to the same page.

The problem it fixes: embedding similarity works on phrasing closeness, not just topic. A clause reading "either party may terminate upon 60 days written notice following an uncured material breach" and a lawyer asking "what happens if they walk away on us" are topically related but far apart in embedding space. Question-to-question comparison closes that gap — a direct, cheap countermeasure to the phrasing-mismatch problem that motivated moving off a single contract-shaped schema in the first place.

Fits with minimal disruption: folds into the existing synthesis call (one new schema field, no new LLM call), writes new embedding rows into the same Tier 1 hybrid pool, dedupe-by-source-page before RRF fusion. Blast radius if the generated questions are systematically off-target is low — purely additive to the candidate pool, doesn't replace anything; grounding and citation checks downstream still catch a bad candidate that slipped through. Gate: log real query hit-rate against question-embeddings vs. page-embeddings once live, drop it if it's not earning its keep.

Document scoping — bare multi-word names & matter references shipped

Gap closed: resolve_scope, the deterministic resolver that pins a question to one document before retrieval runs, had two blind spots of its own. A bare party name with no corporate suffix ("Apex Lumendra Digital") was offered to it one word at a time ("Apex", "Lumendra", "Digital") — each word alone hits dozens of unrelated documents and gets discarded, so the name never resolved. A matter/reference number recited in the question ("MAT-2021-7750") wasn't recognised as a scoping signal at all — and it routinely names several sibling instruments of one deal (a loan agreement, an escrow, an amendment) sharing one matter number, which is correct legal-practice semantics, not ambiguous data. Both fell through to unscoped corpus-wide search, which answered from whichever document happened to sit nearest in embedding space — confirmed live on two questions, each answered from a real but wrong sibling document, different numbers and different parties, stated with full confidence and no hedging.

Fixed with three additive resolvers, verified against the live 572-document corpus and its chat endpoint end to end, not just at the scoping layer: a bare multi-word name is now tried as one phrase before falling back to single words; a matter-reference resolver recognises the pattern, and when it spans several siblings, narrows using whatever else the question names — an instrument type ("the Guarantee agreement"), a filename code ("IMG-4137") — checked against candidate filenames directly rather than repeating a content search. Two collisions surfaced while building the narrowing step itself, both fixed: a bare year in the question ("Jan 2021") coincidentally matched an unrelated matter number embedded in a sibling's filename, and the matter reference itself — being literally embedded in every sibling's own filename — matched all of them and cancelled the narrowing out; purely-numeric tokens and the resolving phrase's own tokens are now excluded from the narrowing set. Zero regressions across eight questions spanning every scope-resolution path (filename, party, party-pair, date, family, matter-reference, corpus-default).

Document scoping — narrowing tokens, party-pairs under code-name titles, compound two-document questions shipped

Gap closed: Three more scope-resolution failures surfaced by continued live testing, each fixed and regression-verified in turn. Narrowing false positives: the AND-of-discriminating-tokens narrowing introduced above was first built as OR-logic, which let generic filename boilerplate ("final", "signed", "draft") pull unrelated documents into a 20-document candidate set. Rewritten to AND — tokens must each match a proper, non-empty subset of candidates — with a real regression caught before shipping: on an empty intersection, an earlier version fell back to "trust whichever token matched the fewest documents," which let a boilerplate drafting-status suffix ("FINAL_FINAL" in a filename) confidently win and return a wrong Lease Deed instead of the real Tax Deed. Fixed by removing the fallback outright — an empty intersection now returns the unnarrowed set, read by every caller as "couldn't narrow," never as an answer. Party-pairs filed under an arbitrary code-name title: when a sibling instrument's title comes from ingest as an arbitrary deal codename ("Matter Blue") rather than a party name, party-pair resolution's title search missed it entirely. A content-search fallback anchors on the rarer party's bare name, content-verifies against the other party's full name phrase (a bare single-word check over-matched — "Tata" alone hit far more than the phrase "Tata Projects" did), then filename-narrows by instrument type with both party phrases excluded from that pass. Compound two-document questions: a question naming two separate documents by two separate parties ("the judgment between X and Y … as stated in the SSA between A and B") let the smaller/more-distinctive party win alone, silently discarding the second reference — confirmed live: a real, fully-indexed judgment was reported as absent because the resolver only ever kept its first pick. Fixed by scanning discarded suffix-derived party candidates (never bare-word fallback names — restricting to real corporate-suffixed names caught a regression where a bare word matching a document-type, not a party, got merged in as a false second document) for a disjoint match, merged in when found.

Structured extraction wired into answer context shipped

Gap closed: get_context, which assembles what the answer LLM actually sees, read only pages.content — the prose summary written at ingest. The clauses/tables typed rows (§ 01.2) were correctly populated but structurally invisible to chat: a page's prose only samples a table's rows for readability, so a pricing question answered from whichever vendor the sampled prose happened to mention, missing the real highest-value row sitting in a second table the prose never quoted. get_context now pulls full clause text and complete table rows directly from their typed stores for every document in scope, tables ordered before clauses (harder to reconstruct from prose than a clause is), verified live against a real ingested pricing table where the answer changed from the wrong sampled vendor to the correct one only once the second table's full rows were visible.

RAG accuracy audit — family-membership blind spot, narrowing self-sabotage, ingest completeness gap shipped

Gap closed: A structured audit — 50 real questions run live, then a further batch scored answer-by-answer against the actual source PDFs, not just against the retrieved excerpt — surfaced three more failures upstream of anything caught by single-question live testing. Family membership silently excluded documents: a family-scoped question ("the Legal Opinions") resolves via page_metadata.doc_family, set by ingest-time content classification — which can disagree with the folder a document was actually filed under. When it does, doc_family lands NULL and the document drops out of every question about its own family, confirmed on a real Legal Opinion whose content reads more like a bare bilateral contract. documents.folder_hint already carries the folder signal at ingest, at zero extra cost — family resolution now unions both signals instead of trusting content classification alone. Narrowing was filtering out its own signal: the token-narrowing step (above) was reusing a stopword list built for a different job — keeping instrument-type words out of party-name candidates — which meant it silently stripped exactly the words it exists to narrow by ("agreement," "data," "processing," "service," "master"). Left with nothing but incidental English ("the term 'Affiliate'") to work with, it collided with an unrelated document's filename ("Term Sheet") and returned it with full confidence. Fixed by dropping that borrowed stopword list from the narrowing path entirely. Ingest-time completeness gap in Definitions extraction: the audit's source-verified scoring caught two documents confidently reporting a definition as "not present" when the defining PDF sentence was sitting in the raw file the whole time — never extracted at ingest, not a retrieval failure. Corpus-wide check found the same gap in roughly 200 more documents. Because this corpus's Definitions boilerplate repeats near-verbatim by design, the fix needed no LLM call at all: a direct regex pass against each affected raw PDF recovered 1,630 Definition clauses across 376 documents (up from 242) at zero inference cost, with the ~40 genuine non-matches (Letters of Intent, Side Letters — document types that never carry this boilerplate) correctly left alone rather than force-fitted.

Document scoping — several party-pairs in one question, and the identifiers a question already states shipped

Gap closed: A re-audit of 51 questions, re-verified line by line against a golden dataset and the source PDFs, found the resolver still losing questions in four distinct ways. Several party-pairs in one question: a comparison names two whole matters at once ("compare the governing law of the KERA between A and B dated X and the KERA between C and D dated Y"), but every party-name detector read the question as one flat list of names — four parties truncated to three and AND-ed into a single title search. Nothing matched all three: one comparison retrieved an unrelated Escrow and SPA, another retrieved one of the two agreements and compared it against nothing, a third retrieved two copies of one side. Such a question is now split into one sub-question per between span — each carrying the instrument phrase that precedes it, handed over at the connector ("and the", "as stated in the") that introduces the next instrument — resolved independently and unioned, and only committed when every pair resolves, so a partial match never displaces a real one. Instrument initialisms: the corpus files a multi-word instrument type under its initialism (KERA, SSA, TSA, IPAssign) while questions spell it out, so the type words matched no filename, were discarded as non-discriminating, and "agreement" — present in most filenames but identifying none — narrowed an 8-document cluster to the 5 that spell the word out, dropping the one KERA the question was about. The initialism is now derived from the spelled-out name and, where it picks out a single candidate, settles the question outright rather than being AND-ed with generic words that cancel it to nothing. Case numbers and dates: "Appeal No. 113/2024 … dated 19 June 2024" carries two of the most specific identifiers there are, and the filename spells out both ("… Appeal No. 1132024-20240619 signed copy.pdf") — but the tokenizer split the case number on its slash into two purely-numeric tokens and discarded both, and read the date as three unrelated words. The question fell through to answering across all 28 Pleadings in the corpus. Both are now rejoined into the orderings this corpus actually files under. A small cluster skipped narrowing entirely: a party match already small enough to return was returned as-is, even when the question stated a date naming one of those documents — so "the Facility Agreement … dated 30 June 2023" returned the loan agreement plus two amendments and an unrelated Tax Deed, and answered about an amendment's governing law, though "30062023" appears in exactly one of those filenames. Gap closed: The Definitions gap above turned out to be one instance of a general pattern: ingest is told to extract "every clause you can identify," and on a long contract it reliably skips the back-half boilerplate — the sections that carry no negotiated value and are exactly what a question naming "Section 12 (Relationship Of Parties)" asks for. Both ingest prompts now require every numbered section to appear as a clause entry, naming the boilerplate that gets dropped, so a fresh ingest does not recreate the gap. One document could not be reached this way — a 43-page scan with no text layer, which is why a definition it states was reported as absent — so the same script takes an opt-in --ocr flag that reads scanned pages through the configured OCR engine, scoped by --only to named documents, since with OCR_ENGINE=azure_vision that is a model call per page while the rest of the script costs nothing. A related correction fell out of testing: citation verification checks quotes against each page's ingest-verified Supporting Quotes block, and the structured-extraction block was not in that corpus — so an answer quoting a clause row, which is stored verbatim by construction, picked up a "read as paraphrase rather than exact wording" note over text that is character-for-character the document's own.

That yields "Figure 1. Floor Plan — the document states 'The diagram below illustrates the floor plan referred to in this Agreement.'", while the diagram itself is an embedded image whose labels never enter the PDF's text layer. Document scoping — compound questions that never repeat "between" shipped

Gap closed: The "several party-pairs in one question" fix above only splits a compound question into per-matter segments when "between" introduces EACH pair — real phrasing routinely skips the repetition ("what does A owe B that isn't in C-D's agreement", "can A and C each assign without B or D's consent"), and the second shape doesn't even keep each matter's two parties adjacent: it lists every "first" party together, then every "second" party. An external accuracy review scored the system 7.1/10 across ten real cross-document questions and flagged exactly this as the dominant failure — three questions answered "the second agreement isn't in the provided context" for documents that were fully ingested and indexed, while every question that stayed within one document scored 9.5–10/10. Root cause was two layers deep: the segment splitter found nothing and fell back to a flat single-pair resolver that truncates four names to three and ANDs them into one title search, matching nothing — and even after teaching that resolver to try every way of pairing the named parties (not just adjacent-in-order, since the "each … without consent of" phrasing groups all first parties together), a separate priority-ordering bug meant single-party resolution still ran first and returned the moment one party's name alone resolved to a document, never giving the compound path a turn. Fixed by trying every possible pairing of the question's named parties, accepting a grouping only when every pair independently resolves to a real, distinct document (declining rather than guessing when more than one grouping would work), and running that check at the same priority as single-party resolution rather than after it. Verified live end-to-end: all three previously-failing questions now cite both agreements with the correct figures for each (e.g. the right reserved-matter indebtedness threshold on each side of a two-JV comparison), and the five already-passing questions were re-verified unchanged.

Document scoping — several documents named by bare nickname, no party name at all shipped

Gap closed: A related but structurally different gap surfaced retesting an eleventh question from the same review: "compare the confidentiality clauses of the Amberline NDA, the Apex Cobalt NDA, and the Apex Falcora EV NDA" answered as if only the Apex Cobalt NDA existed, though all three were real, indexed documents. Ingestion — additive by document, never corpus-level

The fix to "adding 3 docs forces reprocessing all 500": ingestion is a per-document, additive operation against a persistent store, not a corpus-level rebuild. Three mechanics make this real, not just conceptual:

  • Hash-gate at the door — content hash checked against documents before anything else runs. Exact match → skip entirely, zero cost.
  • New-doc-against-existing-index, every merge step — entity/citation resolution fuzzy-matches the new document against the existing entities/entity_aliases table; cross-document relations resolve the new doc's relationships[] against the existing documents registry; wiki-page merging appends to existing shared-concept pages with compaction re-synthesizing only that page past threshold; embeddings insert incrementally into the HNSW index. Cost scales with the new document, never with corpus size.
  • Version/amendment detection — a re-upload that's clearly a new version of an existing document writes an amends/superseded-by edge and flips the old document's lifecycle tag automatically, rather than landing as an unrelated new document.

§ 01.6 new

Production Hardening

From a senior-architect audit of the plan so far. Everything below is scoped as accommodate-now: cheap to build into tables and pipelines that don't exist yet, expensive to retrofit once they do — or trivial floor-level hygiene with no reason to defer. A separate, larger set of findings was deliberately deferred; see the callout at the end.

Concurrency & race conditions

Everything designed so far assumes sequential operation. It isn't, once bulk upload and background re-ingest run in parallel. Scoped down to what actually matters at current single-user scale — not the full multi-user version.

Entity canonicalization race

check-then-act

Two documents ingesting in parallel, both mentioning "Acme Corp" for the first time — both check entities, both find nothing, both create a new row. Fix: a unique constraint plus upsert (or advisory lock) on the canonical-name key, not a plain look-up-else-create.

Compaction race

concurrent write

Two concurrent appends to the same wiki page could both cross the re-synthesis threshold and trigger compaction at once, producing two competing rewrites. Fix: per-page lock during compaction.

Active-wiki binding

mutable global

The active-wiki pointer (Wikis) is a mutable global — if admin switches wikis mid-request, a request that started resolving against wiki A could finish reading from wiki B. Fix: wiki_id bound once per request at entry, carried through the whole call, never re-read from a live pointer mid-pipeline.

LLM output is untrusted input — treat it that way

  • Schema validation/coercion before write — nothing today rejects or coerces a malformed LLM response. A model returning a string where a date or currency field is expected would either fail silently or corrupt a typed column. A validation layer sits between LLM output and DB write; a failed field drops confidence and routes to the Review Queue rather than being trusted and inserted raw.
  • Retry / idempotency — an extraction call that times out or errors mid-segment needs a retry path that can't double-write partial structured rows. Matters most once background re-ingest jobs run unattended.
  • Confidence scores are self-reported by the same model doing the extraction — LLMs are known to be poorly calibrated, often overconfident on exactly the cases they get wrong. The entire Review Queue stakes-tier system rests on this number meaning something. Worth a periodic calibration spot-check — sample high-confidence extractions, verify manually, see if confidence actually tracks accuracy — rather than assuming it does.

File-upload validation shipped

Malformed or malicious PDFs — decompression bombs, corrupt structures designed to hang pypdf or Tesseract — can cause resource exhaustion before any content-level defense even runs. A validation/sandboxing gate belongs at the front door, before parsing starts, not after.

Shipped

Built on target-architecture-v2 as services/upload_validation.py, called synchronously in /upload right after each file is saved and before it's queued to the ingest executor. Checks, in order: non-empty and under a per-type size cap (50MB PDF / 25MB DOCX / 10MB TXT, env-overridable); magic-byte match against the claimed extension (%PDF-, the DOCX zip header) so a renamed non-matching file is rejected outright; then a structural probe — PdfReader opened, rejected if encrypted or over a 2000-page cap, and page 0's content stream actually decoded (a decompression bomb blows up here, not at open time) — run in a worker thread with a hard timeout so a hostile file can't hang the request. A rejected file is deleted immediately and never reaches wiki.ingest; the reason is returned to the frontend per-file instead of failing silently.

Login hardening

Floor-level hygiene, not deferrable even at single-user scope: password hashing (bcrypt/argon2, never reversible), rate-limiting on login attempts, HTTPS-only session cookies.

Encryption at rest

Document content and extracted structured data encrypted at rest by default. Real client documents will land in wikis eventually — privileged, confidential legal material — and this needs to be on from day one, not bolted on once client data is already flowing in.

Cost pre-flight gate on bulk operations shipped

Per-run caps already exist (Review/Compare hard-capped at 20 docs, broad retrieval has a total cap) — but nothing stops a large batch operation from firing an uncapped burst of calls. Before executing bulk re-ingest, a wiki-wide reprocess, or any operation above a document-count threshold, estimate the call count/cost and require explicit confirmation — the same instinct as the 20-doc cap, applied one level up at the operation level rather than the per-run level.

Shipped

Built on target-architecture-v2 as services/cost_estimate.py, wired into both existing bulk entry points: /upload and /resume_ingest (re-ingest-by-family and wiki-wide reprocess don't exist yet — they'll get the same gate once built, via the same shared helper). A batch of ≥3 files, or an estimated cost ≥$0.25 (both env-overridable), is held — files saved and registered, but not queued to the ingest executor — until the caller re-POSTs with confirm=true; the frontend shows the estimate and asks. Call-count is exact, not guessed: it replicates wiki._SINGLE_CALL_THRESHOLD's single-call/overview+detail branching and calls wiki._split_segments directly rather than re-deriving it, so the estimate can't silently drift from what ingest() actually does. Token/cost figures are a deliberately conservative approximation (each call's configured max_tokens ceiling, public list pricing for the configured deployment) — a pre-flight warning, not an invoice. The whole module makes zero LLM/embedding calls itself; verified via the DB-mode test client that a 3-file batch is held with nothing written to pages until confirmed.

Deferred — real cost, matters at a scale not reached yet

Named in the audit, deliberately not built now: HNSW index vacuum/reclaim job (matters at real deletion volume), embedding-model version tracking (matters on model upgrade), re-ingest dry-run/rollback and diff-before-commit, a "flag this answer as wrong" feedback loop back into the Review Queue, basic observability (ingestion failure rate, Review Queue backlog size), schema/code version skew during rolling deploys, amendment-ordering and re-ingest-vs-live-read races, and third-party LLM data-exposure handling for privileged content — a vendor/compliance decision to make before real client data flows in, not a code change to make now.

New fast-path branch

Query decomposition new

The router gap named earlier in this doc — "each fast-path branch has its own detector, no unified mechanism" — gets sharper on a compound question: "which supplier contracts allow termination after a change of control and have less than 30 days notice" is a comparison-to-standard clause, a relation, and a filtered exhaustive-set query stacked together, and no single branch above answers it whole. What the verification pass found. Everything above was checked without spending an LLM call except one deliberate live ingest, and two defects came out of it.

  • A right filed as a duty. The one real ingest returned two obligations for an escrow agreement. The first was genuine; the second was "may set off any amount owed to it … against any amount payable" — a right the agreement grants, recorded as a duty it imposes. The prompt already said a grant of a right is not an obligation, and the model returned one anyway. That reversal is the worst thing this table can carry, so the rule is now enforced in Python as well as asked for: a permissive opener with nothing negative attached is dropped, since "may not disclose" is a prohibition and a genuine obligation. The guard logs when it fires — otherwise there is no way to tell the prompt working from the guard carrying it.
  • Two silent export buttons. Both CSV exports returned without a word on an empty table. For the tracker that is the common case, not the rare one, so the button read as broken.

What held. Wiki isolation, the failure mode this doc records under Phase 0: switching the active wiki took the register from 572 documents to the default wiki's own 7 — 4 contracts, 2 litigation, 1 opinion, matching the database exactly — and back, with the obligation denominator and standard_cell scoping with it. The 1,350-document ingest and accuracy audit. The corpus went from 572 to 1,384 documents / 91,050 pages with zero ingest failures, and was then measured against a 700-question set graded on both the ground-truth answer and the expected source document: 86.3% answer-correct (603/699), 87.5% source-document-correct, 95.0% of quoted spans verified against the retrieved context. The failure split matters more than the headline — of 96 wrong answers, 71 declined and only 25 asserted something wrong. Trap questions, where the right answer is a refusal, scored 73/75. Separately, all 843 pending high-stakes clauses were checked against their source PDFs: 830 (98.5%) are verbatim-present and none were fabricated — every rejection was a mislabelling, such as a clause filed as Force Majeure Termination whose text describes a 30-day resumption trigger and never mentions force majeure.

Four defects the audit surfaced, all since fixed. Each had been silently true for the whole life of the corpus.

  • Compaction had never run once. run_compaction takes a per-page lock, then re-reads the page under it to confirm it is still due. That re-read called db.get_page(), which never selected append_count — so the check read it as 0, always concluded "no longer due", and skipped every page, while still paying a lock acquisition and a re-read per candidate on every ingest. In one run that was 8,604 round-trips for 0 compactions, roughly 90% of wall-clock time against only 74 real LLM calls. With the column restored the whole backlog cleared: 274 of 274 pages, 11.7 minutes, no failures. 99b9811
  • Document metadata extracted, then discarded. Every family extraction produces parties, effective date, expiry and status, validates them, and writes them into the typed table's typed_value blob. Nothing ever promoted them onto the documents row: upsert_document accepts those columns and was only ever called with family, type, jurisdiction and the content hashes. All four sat at 0% populated across all 1,384 documents — and the Contract Register and Obligation tracker read exactly those columns, so both were reading empty fields while the data sat one table over. Backfilled from the existing blobs with no LLM calls: effective_date 0 → 1,204, parties 0 → 1,336. ac42c82
  • Duplicate detection ran after OCR, not before. The check compared extracted text, so a re-uploaded scanned document paid for full vision-OCR before anything recognised it — and OCR is the expensive part for exactly those documents. Now the raw file bytes are hashed before the reader runs. On the 1,358-file upload, 484 duplicates were skipped at zero cost. 080bae3
  • "Closest precedent" questions could not be expressed by retrieval. Retrieval embeds the question, so every page it returned belonged to the single document the question named, and the model correctly reported it had nothing to compare against — 0 of 4. A document-to-document search now averages the anchor's page vectors and ranks the corpus against that centroid, restricted to the same instrument type. Anchor selection prefers the doc_type named in the question over raw page-hit count, without which a Software License Agreement query resolved to a Legal Opinion. 0/4 → 4/4. a106763 This is the Precedent layer arriving early, in narrow form, from Phase 2 below.

Two gaps that are not code defects. Milestone questions ask for a contract value no document states — it is the sum of a milestone schedule — so it is now computed in Python rather than by the model, and asserted only when the milestone percentages account for ~100% of the contract, which is what proves the whole schedule reached context rather than a fragment (06d9f7d, 0/5 → 3/5; the remaining two retrieve a partial schedule and the guard correctly refuses to state a total). The 13 group-ownership questions ask what percentage one Apex entity owns of another "according to the Apex Group ownership structure": no such document is in the corpus, and no ownership percentage for those entities appears anywhere in 91,050 pages. The system declined every one, correctly. That is a missing source, not a missing feature, and no retrieval work will close it.

The sixteen "scanned source" failures were not an OCR gap. They were recorded here as needing re-OCR. Re-ingesting all thirteen that still have a file on disk closed none of them, and checking why settled it: OCR runs correctly — a vision call fires and returns coherent text — and the expected answer is in none of the sixteen documents' bodies. Two files are gone from disk; nine are genuinely scanned and OCR reads them fine; five carry a thin but complete text layer, one being a 277-character judgment that states no date at all while the ground truth ("17 November 2022") appears only in its filename. These sit with the thirteen group-ownership questions: the corpus does not contain what the test set asks for, and no retrieval, OCR or extraction work reaches them.

A defect that re-ingest itself introduced, found by running it. The first version cleared a document with delete_document_data, which removes every page whose source_doc names it — and that column records only the last writer, so merged concept pages built mostly by other documents carry the name of whichever wrote last. Four documents whose text layers hold 248–1,860 characters were each credited with 12–13 pages; clearing them cost 36 pages of merged content that re-ingesting one document cannot rebuild, because it only re-contributes its own share. The corpus went 91,050 → 91,014 and those pages are not recoverable from any single re-ingest. Now fixed: only pages written once are deleted, using variants as the discriminator — it holds one entry per contribution and is NULL exactly on single-contributor pages, which separates 17,898 exclusive pages from 742 shared ones. Shared pages are left for the merge to blend into, that being the right trade against deleting other documents' work. On a real document owning 18 pages, 16 of them shared, the old path deleted all 18 and the new one deletes 2. Recorded rather than quietly fixed because the loss is real and was caused here, and because at family scale — 919 contract documents — the same bug would have been severe.

Phase 3.5Normalization — blocks most of Phase 4/5 prerequisite

Phase 4 and Phase 5 are written on the premise that the numbers, dates and clause types they need are "already typed and shipped." Measured against the live 1,383-document corpus, that premise does not hold yet — and this phase is what makes it true. Four findings, each checked directly against legalwiki_v2:

1. clause_type is free text, not a vocabulary. 5,956 distinct values across 31,457 clause rows — roughly one new type per five clauses. Definitions, Definition, Definition - Affiliate, Liability Cap, Liability cap, Aggregate Liability Cap, Exclusions from Liability Cap all coexist as distinct types. Playbooks already compensates with keyword matching rather than equality (services/playbooks.py:clauses_for_rule) — which means a "Liability Cap" rule reduces to the single keyword liability and then assesses Exclusions from Liability Cap, General Liability Exclusion and Continued Liability for Subcontracted Work against a cap standard they were never meant to be judged by. That is a confident wrong finding produced by design, not by a bad model. A canonical type per clause (raw LLM label preserved alongside as a subtype, never discarded) fixes this, and is the same field Phase 4's gap-detection and the clause sub-attribute schema both have to key off.

2. The typed values are not queryable. clauses.typed_value is populated on 8,620 of 31,457 rows (27%), and its shape is LLM-invented per row — {'notice_period': '60 days'}, {'basis': …, 'duration': 'two (2) years'}, {'steps': [...]} — no shared key set to query. contracts.liability_cap (387 of 951 rows) mixes structured JSON {"amount": 25529937.0, "currency": "INR"} with whole prose sentences and with "the cap agreed in Schedule IV", in the same column. obligations.deadline is prose — "not less than 90 days' prior written notice", "within 72 hours", "prior to commencing work" — and obligations.notice_period is populated on 87 of 4,730 rows (1.8%). SUM/AVG over liability caps, NOT-EXISTS gap detection, date-bucketed trend queries and both Phase 5 agents all assume columns that can be compared and arithmetic'd. Normalizing money, duration and date into real typed columns beside the raw text — never replacing it, the raw string stays the citable source — converts every one of those from blocked to trivial.

3. Duplicate documents are ingested silently. documents.file_hash is computed but not enforced: four byte-identical pairs are live in the corpus right now, each a plain PDF and its separately-run _ocr.pdf twin under both filenames. A fifth pair was found and removed by hand while fixing the amendment-scope resolution — and removing it exposed that the whole-document delete path had never been updated past its original table set, orphaning rows in nineteen tables including the documents row itself (since fixed). Duplicates double-count in every aggregate this roadmap proposes and can return the same clause twice as if it were corroborating evidence from two documents.

4. Nothing measures whether answers got better. Every phase so far has been verified by building the thing and checking it works — not by measuring the answer quality it was meant to improve. The stated goal is that bad answers become rare; that is currently an assertion, not a number. A held-out question set with verified expected answers, scored on a fixed rubric and re-run after each change, is what turns it into one — and it is the only item here that tells you whether the rest of this roadmap actually paid off.

Phase 5Specialist deterministic tools planned
Calculation Agent · Date/Deadline Agent

Two deterministic tools, not new RAG pipelines — both read from the same backbone everything else does. Calculation Agent computes a derived value (liability cap in rupees, prorated fee, penalty amount) from a stated formula plus already-typed values, via a Python calculation tool rather than LLM arithmetic in-context — distinct from Phase 4's Aggregation, which sums stored numbers rather than computing a derived one. Both are gated on Phase 3.5. The principle is right and worth keeping — a calculator is exactly the correct answer to LLM arithmetic, which is the single hardest error class for a reader to catch. But "already-typed values" and "the Obligation tracker's stored dates" describe a state the corpus has not reached: obligations.deadline holds "not less than 90 days' prior written notice" and "prior to commencing work", and notice_period is populated on 1.8% of rows. Build the normalization first and these two become small; build them first and they inherit the ambiguity they were meant to eliminate.

§ 08

Net effect — what actually changes, honestly

Ingestion gets heavier — compounding, not replacing. The original Part 2 estimate was +20–50% ingest LLM cost from one extended structured-output call. This revision stacks a further +10–20% on top of that, driven almost entirely by the new doc-type classification pre-pass (a new short call, every document, not just long ones) and the fatter main schema — not by each new extraction category costing separately, since most of them (structural anchors, jurisdiction, citations, entity match) fold into the existing call at near-zero marginal cost.

Table and image extraction is a genuinely new cost line, not a delta on an existing one — real vision-model calls, scaling with corpus table/image density, currently unmeasured.

Query gets lighter for structured question types — simple fact lookups, exact clause questions, filtered cross-document lists, obligation checks, cross-document relation queries, and structural/citation lookups all become mostly database reads with a light synthesis call. Complex comparison, playbook reasoning, and precedent drafting still need the full LLM pipeline.

Review and Compare Mode stop scaling with (documents × columns). Once standard columns resolve from clauses/obligations and Compare Mode gets the same cache check, only genuinely novel columns still cost a call — bounded by how many a lawyer types in, not by corpus size.

At the real operating scale — 20 documents per run — the numbers stay trivial. Worst case: ~₹10 on gpt-5-nano, ~₹26 on gpt-4o-mini. A realistic run: ~₹0.60 on gpt-5-nano, ~₹1.50 on gpt-4o-mini.

A filter re-evaluates on every read, so a playbook run and the dashboard row recording it could cover different documents as the corpus grows — and a recorded run that cannot be reproduced is not evidence of anything. Filters populate a collection, evaluated once; they are not the collection. Unknown document names are counted and returned rather than skipped, since a typo would otherwise build a collection that looks populated and runs over nothing.
    • Playbooks. Pulling a clause is a DB read — ingest already persisted 31,478 of them — so a run spends inference only on the judgement, and the route counts matching clauses up front to price a run exactly rather than by extrapolation. Rules match clause types by keyword, not equality: extraction writes free-form names, 5,957 distinct across this corpus with "liability" alone under 128 spellings, and a rule keyed to one exact string would assess nothing while reporting no deviations — indistinguishable from full compliance, which is the worst failure this feature can have. A rule with no matching clause records missing, a finding in its own right; a failed or unparseable classification records unclear, never a guess, because on a deviation report a wrong verdict is worse than an absent one. Runs freeze the document list they covered rather than pointing at a collection, since membership changes. Live over 5 documents: 25 findings — 6 unacceptable, 4 missing, 3 standard, 12 unclear — with specific rationales ("excludes key liabilities, creating uncapped exposure") and concrete redlines. The high unclear rate is correct: those clauses defer their cap to an unquoted schedule, so the amount genuinely cannot be determined from the text.
    • Precedent layer. Drafting needs the clause that solves a problem, not the page that discusses it — a page vector averages a whole topic, so "liability capped at fees paid" ranks a page about liability above the clause that says it. Roles decide what is draftable: contracts and term sheets are precedent; judgments, opinions and authorisations are reference and are never embedded at all, because a judgment quoting a liability cap is describing someone else's contract rather than offering a house position. Derived from family with no LLM call (948 precedent / 429 reference) and never overwriting a manual tag, which is the one thing the heuristic cannot reconstruct. All 30,075 eligible clauses embedded, 43.8 min, no failures; every vector carries role precedent, and no reference-family clause surfaced in any test query.
  • Draft Mode and the Ask tab's drafting intent both switch to clause-level embeddings, scoped to role-tagged precedent documents. shipped The "silently losing wiki grounding" history now has a measured cause. The page path selected up to 15 whole pages and cut the result to a 4,000-character budget, so what reached the model was whichever pages sorted first and whatever survived the cut — the grounding was being truncated off the end of the context. Twelve ranked precedent clauses for a real drafting request come to 5,249 characters: under the old cap roughly a quarter of that would have been discarded, unseen. The budget is now a clause count, because the retrieved unit is already chosen for relevance and there is nothing to truncate. One request reached six different type spellings — "Limitation - aggregate cap", "Limitation Cap", "Limitation of Liability", "Aggregate Liability Cap" — which no page-level or string match reaches. Falls back to the page path when no vectors exist, so a corpus without the layer still drafts rather than drafting from nothing.
Phase 3Depends on Phase 2
  • Deviation Dashboard (SQL aggregation over playbook_findings). shipped No new tables and no LLM calls — the whole feature is turning rows a playbook run already wrote into "which documents need attention, ranked, with why". Two shapes: an overview (one line per playbook, its latest complete run, sorted by unacceptable + missing count so the worst playbook surfaces first) and a per-run breakdown — by clause type, by document worst-first, and a priority list restricted to unacceptable/missing ordered by severity. Only completed runs are aggregated, deliberately: a run still in progress has partial findings, and surfacing it would show a document as compliant simply because its clauses have not been reached yet. Stale-document detection compares a run's frozen documents_covered against the collection's current membership — this is why runs freeze that list rather than pointing at a live collection (§ Playbooks, above): without a frozen snapshot there is nothing to compare the present against. A document added to a collection after the run shows up as "not yet assessed" rather than silently reading as compliant. Verified against real leftover data from the earlier live Playbooks test — 25 findings across 5 documents — with every aggregation cross-checked against a manual SQL query rather than merely checked for a non-empty result, including adding and removing a document from the live collection to prove the stale flag actually reacts to membership changes rather than being computed once and cached.
  • Prompt library. shipped The spec names this under "Also fixing" with no further detail — a smaller item than the seven locked-in features — so scope was kept correspondingly narrow rather than invented: named, wiki-scoped templates carrying {{placeholder}} variables, CRUD, and a render endpoint. Distinct from the existing House Rules (services/rules.py), which are global answer-style instructions silently appended to every prompt — this is a library a person picks from for one specific request, so it lives per wiki rather than in one shared global file. Rendering never blanks a missing variable: an unfilled {{placeholder}} is left literal in the output and named in a missing list, because a half-filled template that still shows what is missing is safer to hand someone than one with a silent gap where a name should be.

118 tests across both features, zero LLM calls — the Deviation Dashboard is a pure read over existing rows and the Prompt library is CRUD plus string substitution, so nothing here needed inference to verify. Each piece shipped as its own commit — service, then routes, then UI — tested clean before the next.

Phase 3.5Normalization — gates most of Phase 4/5
  • Canonical clause vocabulary. A controlled clause_type set with the raw LLM label preserved beside it as a subtype — never discarded, since the raw string is often more specific than the canon and is what a reviewer recognises. Today: 5,956 distinct free-text types over 31,457 clause rows. Map at ingest (cheap string/embedding match against the canon, no extra LLM call), backfill existing rows in one pass. Immediate payoff independent of Phase 4: Playbooks stops keyword-matching. Right now clauses_for_rule reduces a "Liability Cap" rule to the keyword liability and assesses Exclusions from Liability Cap and General Liability Exclusion against a cap standard — a wrong finding the model never had a chance to get right.
  • Normalized value columns. Parse the already-extracted strings into comparable columns beside the raw text: money into amount/currency, durations into a day count, deadlines into a date or a typed offset ({n_days, basis, business_days}). Raw text always stays — it is the citable source and the fallback when parsing declines. Deterministic parsing, no LLM call. Today contracts.liability_cap mixes JSON, prose and "the cap agreed in Schedule IV" in one column; obligations.deadline is prose; clauses.typed_value is 27% populated with per-row invented key shapes. Parse failures must record as explicit unparsed, not as NULL — a NULL is indistinguishable from "no cap exists", which is exactly the wrong answer for gap detection to return.
  • Ingest-side duplicate detection. documents.file_hash is already computed and already unenforced — four byte-identical plain/_ocr pairs are live in the corpus now. Reject or merge on hash collision at upload. Duplicates double-count in every aggregate this phase enables and can surface one clause twice as if two documents agreed.
  • Accuracy regression suite. A held-out question set with corpus-verified expected answers, scored on a fixed rubric (relevance / hallucination / accuracy) and re-run after each change. Covers the archetypes and the known-hard cases — compound party-pair scope, bare-nickname documents, amendment chains, and the abstention cases where the right answer is "not established in these documents." Costs real LLM calls per run, so it runs per milestone rather than per commit. This is the only item in the roadmap that answers whether any of the rest of it worked.

Why this exists as its own phase: it was not in the original plan and was not surfaced by brainstorming — it came out of measuring the live corpus while fixing an unrelated retrieval bug. Every numeric and gap-shaped item in Phases 4 and 5 reads as cheap on paper because the data is described as "already typed"; it is already extracted, which is not the same thing. This phase is the difference between the two, and it is mostly deterministic parsing rather than new model work.

Phase 4New archetypes — not started
  • Aggregation / computation — SUM/AVG/COUNT over the typed numeric fields exhaustive-set queries already read. Route as a new Structured Lookup branch (Fig. 2), same mechanism as the existing fast-path checks. Gated on Phase 3.5 — the columns are not comparable today.
  • Gap / absence detection — NOT EXISTS / NULL check over the same typed tables, mirror of exhaustive set in the opposite direction. Gated on Phase 3.5 — and specifically on unparsed values recording as unparsed rather than NULL, or "we could not read this cap" returns as "this contract has no cap."
  • Precedent / similarity lookup, read-only — expose the Precedent layer's existing retrieval as its own answerable question, separate entry point from Draft Mode, no drafting step. Unblocked today — start here.
  • Trend / statistical over time — date-bucketed aggregation, combining the temporal and aggregation query shapes. Gated on Phase 3.5.
  • Unsupervised batch risk-scan — aspirational, not scoped for a build estimate yet. No predefined standard to check against; closer to Open Discovery's LLM-heavy territory, scoped to a batch rather than a single question. Needs its own design pass before a checklist item is meaningful.
  • Query decomposition — break a compound question into sub-tasks before routing, send each to the cheapest capable path. What makes the archetypes above actually compose on a real multi-part question rather than answer in isolation.
  • Defined-term cross-reference — defines/references-term edges, same synthesis call as other relations.
  • Document QA warning — surface low-confidence pages to the lawyer directly ("page 27 could not be reliably interpreted"), backed by richer per-page OCR provenance (engine, confidence, skew, language). Unblocked today — start here. Correction: this provenance is not "already being stored at ingest" — the only per-page quality signal in the schema is pages.char_count; there is no OCR engine, confidence, skew or language column anywhere. The columns are new work, and this is the highest-value accuracy item on the list because the failure it catches is already known to have happened silently on real documents in this corpus — several scanned PDFs extracted 0–2 usable pages and were answered against anyway, with nothing telling the reader the document was effectively unreadable.
  • Clause sub-attributes — structured fields per high-value clause type (liability cap → cap_present/cap_type/uncapped_exceptions[]), reused by Playbooks/Review/Compare/Risk instead of each re-interpreting clause text independently. Gated on Phase 3.5's canonical vocabulary — there is no stable clause_type to key a per-type schema off today. Note the uncapped_exceptions[] field is doing double duty: it is also the direct fix for the Playbooks keyword-overreach problem, since "Exclusions from Liability Cap" stops being a separate mis-assessed clause and becomes a field on the cap itself.
  • Named, bounded-hop relation functions — replace open joins on the relation fast path with typed operations (find_change_of_control_terms() etc.), hop-capped at 3. Governance rather than accuracy — worth doing, lowest urgency on this list.
  • Explicit latency targets — added to § 08 as a companion to the existing cost figures, for the still-outstanding pipeline instrumentation to check against.

Note: the first four are query-router additions on top of the existing backbone — no new tables, no new ingestion work, same class of change as wiring temporal/comparison-to-standard into Ask mode (§ 05). The six items below them, from a second brainstorm pass, are a mix of router (decomposition), extraction (defined-term, clause sub-attributes), and ingestion (Document QA, OCR provenance) work — each scoped to extend something already shipped, not a new subsystem. External regulatory compliance was considered for this phase and explicitly held out — see the callout at the end of § 05.

Phase 5Specialist deterministic tools — not started
  • Calculation Agent — deterministic Python tool for derived legal-math values (liability cap in currency, prorated fees, penalties) from a stated formula plus already-typed values. Never LLM arithmetic when a calculator can do it exactly.
  • Date/Deadline Agent — deterministic date-math tool (business-day offsets, notice-window calculations), layered on the Obligation tracker's stored dates.

Both are tools the router calls, not new retrieval pipelines of their own — same backbone, same principle as everything shipped so far: precompute and compute deterministically wherever possible, reserve the LLM for what genuinely needs reasoning.
